# Встановлення, міграція та оновлення

## Підтверджений перехід 16.10.2026

Чинне встановлення переведено на HACS **v0.2.1** (перевірений коміт `d79262f278d3613433469951805570cdc40d0a16`). `sensor.heating_ui` підтвердив джерело `/homeassistant/appdaemon/apps/ha-heating-ai` та збіг SHA-256 усіх дев’яти модулів. Є свіжий heartbeat і прогноз із `planning_policy_version: 4`; параметри навченої моделі збережені.

У `/config/apps/heating_ai_hacs` створено звичайний каталог із дев’ятьма файловими посиланнями на HACS. Старі модулі збережені в приватних резервних копіях поза apps. Локальний YAML і `/config/heating_data` залишилися на своїх місцях; одноразову команду міграції в параметрах AppDaemon прибрано. Для цього встановлення надалі застосовується розділ «Подальші оновлення», первинний перехід повторювати не потрібно.

Панель має адресу `/heating-ai`, показується в бічному меню та відкривається ярликом із `climate-control`. Ресурс `/local/heating-ai/loader.js` зареєстрований один раз; файли інтерфейсу оновлюються самим застосунком.

Це **AppDaemon-застосунок**, а не інтеграція HA Core. HACS доставляє всі дев’ять Python-модулів та упакований інтерфейс. Наявні helpers, датчики, резервна автоматика та кеш погодинної погоди є передумовами. HACS їх не створює. Приклад конфігурації містить заглушки й вимкнені команди; він не налаштовує конкретний будинок.

## HACS

1. У налаштуваннях HACS увімкнути **Enable AppDaemon apps discovery & tracking**.
2. У **Custom repositories** додати `dragonidf/ha-heating-ai` з типом **AppDaemon**.
3. Завантажити перевірений реліз. Перевірити commit релізу та результат Tests.

HACS зберігає застосунок у `appdaemon/apps/ha-heating-ai` відносно конфігурації HA. Це ім’я репозиторію; воно відрізняється від `apps/heating_ai` всередині Git. [Правила HACS](https://www.hacs.xyz/docs/publish/appdaemon/).

У Home Assistant OS сучасний AppDaemon має власний `/config`, а конфігурація HA змонтована як `/homeassistant`. Типовий HACS-шлях у AppDaemon — `/homeassistant/appdaemon/apps/ha-heating-ai`. **Перед міграцією прочитати реальний app_dir і перевірити mounts.** Не змінювати глобальний app_dir навмання: він обслуговує також інші застосунки.

## Первинний перехід із прямого встановлення

Мета: одна реєстрація контролера, модулі фізично в HACS-каталозі, чинний локальний YAML та абсолютний data_dir поза керованим каталогом.

1. **Інвентаризація.** Прочитати конфігурацію AppDaemon й локальний YAML контролера. Зафіксувати module, class, app_dir, data_dir, allow_actuation, entity_id режиму/дозволу команд/вентилятора. Знайти всі копії семи старих модулів і всі YAML-реєстрації HeatingClimate. Повинен залишитися один контролер. Не публікувати значення секретів.
2. **Резервування й призупинення.** Зберегти код і локальний YAML у приватній резервній папці поза app_dir. Записати поточні режим та armed; призупинити команди моделі через чинний helper і перевірити стан. Зупинити **AppDaemon**, щоб багатофайлова заміна не спричинила часткове завантаження. HA Core перезапускати не потрібно.
3. **Дані.** Залишити чинний абсолютний data_dir без змін. Не переносити й не перезаписувати state.json, telemetry.jsonl, енергетичні лічильники, навчені коефіцієнти або Recorder. Особистий YAML і резервні копії залишаються локальними.
4. **Підключення.** Старі сім .py забрати зі сканованого app_dir у резервну папку. Під’єднати HACS-каталог до чинного app_dir через звичайний каталог `heating_ai_hacs` із посиланнями на кожен із дев’яти .py файлів. Локальний YAML залишається на старому місці, поза HACS. `module: heating_climate` та `class: HeatingClimate` не змінюються. Оновлення HACS змінює файли за посиланням, а не другу незалежну копію.
5. **Запуск.** Запустити AppDaemon. Переконатися, що немає ImportError, дубліката HeatingClimate, помилок доступу до даних або UI. Відновити записані режим та armed після перевірки стану. Інші застосунки та їхні YAML не змінювати.
6. **Доказ робочого шляху.** Перевірити `sensor.heating_ui`: версія 0.2.1, source_directory відповідає HACS-каталогу, module_hashes збігаються з дев’ятьма файлами конкретного релізу. Перевірити свіжий heartbeat, поточну модель, енергію, термостат, прогноз і `planning_policy_version: 4` у sensor.heating_forecast. Старий heartbeat або лише завантаження HACS не є доказом міграції.
7. Під’єднати [вебпанель](web-panel.md), перевірити живі значення, три вкладки, історію та погоду. Якщо File editor тимчасово отримував розширений доступ, повернути enforce_basepath=true та зупинити його.

### Утиліта міграції

`tools/migrate_hacs.py` автоматизує лише крок із файлами. Її запускають з окремого термінала/середовища, де видно обидва каталоги; шлях цілі посилання має також існувати всередині AppDaemon. Вона не керує HA або Supervisor, не редагує YAML, не перемикає helpers і не перезапускає сервіси. Спочатку виконати інвентаризацію та призупинення вище.

Це **приклади шляхів**; замінити їх перевіреними шляхами свого середовища. Спочатку виконується лише перевірка:

```sh
python tools/migrate_hacs.py \
  --app-dir /app_configs/a0d7b954_appdaemon/apps \
  --hacs-dir /homeassistant/appdaemon/apps/ha-heating-ai \
  --data-dir /app_configs/a0d7b954_appdaemon/heating_data \
  --backup-dir /app_configs/a0d7b954_appdaemon/heating_migration_backups
```

Після зупинки AppDaemon повторити команду з `--apply --appdaemon-stopped`. Прапорець — підтвердження оператора, а не автоматичне виявлення зупинки. Утиліта перевіряє комплектність HACS, дублікати та розміщення даних; створює резервні копії коду й перевіряє SHA-256, перш ніж змінювати шляхи. Виведений migration.json зберегти локально. YAML резервувати окремо: він не змінюється утилітою.

Якщо термінал не має потрібних mounts або не може створити посилання підтримуваним способом, спочатку налаштувати доступ і перевірити шляхи. Не використовувати File editor command endpoint для виконання коду.

## Подальші оновлення

Після підтвердженої первинної міграції:

1. Зберегти поточні режим/armed і резервну копію коду; перевірити commit релізу.
2. Призупинити команди й зупинити AppDaemon на час багатофайлового оновлення, щоб не завантажувалися змішані версії.
3. Оновити Heating AI через HACS. Він має перезаписувати каталог, показаний у source_directory.
4. Запустити AppDaemon; перевірити версію/хеші, свіжий цикл, planning_policy_version, прогноз і журнал; відновити початкові режим/armed.
5. Оновити сторінку вебпанелі. Завантажувач підхопить новий файл інтерфейсу. Дані й налаштування залишаються локальними.

## Відкат

**Після HACS-оновлення:** призупинити команди, зупинити AppDaemon, завантажити попередній перевірений реліз у HACS, запустити AppDaemon, перевірити цикл і відновити попередні режим/armed. Для версії без вебпанелі повернутися до чинного climate-control.

**Після первинної міграції утилітою:** зупинити AppDaemon й виконати:

```sh
python tools/migrate_hacs.py --rollback /path/to/migration.json --appdaemon-stopped
```

Утиліта перевіряє незмінність посилання й резервних копій, прибирає посилання на файли та відновлює старі модулі. Запустити AppDaemon, перевірити цикл і відновити записані режим/armed. Резервні копії залишаються. **Дані навчання, телеметрію й енергію разом із кодом не відкочувати.**

AppDaemon не обходить символічне посилання на цілий каталог. Використовуйте окремі файлові посилання всередині звичайного каталогу. Для AppDaemon App на HA OS їх можна створити одноразовою перевіреною командою в офіційному параметрі init_commands: перед запуском перевірити ціль і кожен шлях, після запуску повернути попередній список init_commands. File editor command endpoint для цього не використовується.
