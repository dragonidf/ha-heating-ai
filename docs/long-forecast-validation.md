# Довгий прогноз, вимірювання та історичний графік — 0.3.17–0.3.19

## Прогноз під час зникнення електрики — 0.3.19

Після реального зникнення мережі 02.11 близько 23:00 доступні кімнатна
температура й обратка, але електричний баланс став невідомим. У 0.3.18
спільний `quality` для виконання й прогнозу через це публікував порожню
криву. Це не збій процесу: heartbeat і control_health лишалися справними.

Планування тепер вимагає придатних теплових входів, а право команд — як і
раніше, підтвердженої мережі, вимірів та чинних safety guards. Невідомі вати
не стають нулем і не потрапляють у точний облік або навчання. Прогноз має
`electrical_inputs_unavailable`, `grid_state`, `return_estimated` і не
отримує `validated=true` за невідомої потужності.

За відсутньої обратки під час off/unknown мережі дозволений попередній
stored-heat observer, якщо його стан придатний і не старший доби. Він
продовжує охолоджувати запас за чинною моделлю; це не свіжий вимір probe.
Якщо немає ні придатної обратки, ні збереженого запасу, новий прогноз не
вигадується. Втрата й повернення фактичної мережі скидають таймер повного
розрахунку, зберігаючи негайну заборону heat на off/unknown. UI пояснює
живлення раніше за загальне повідомлення про нестачу вимірів.

Живе вимірювання історії 0.3.18: перша сторінка холодного 7-денного запиту
26,701 с (до: 26,318 с), повторний запит того самого діапазону з кешу
4,106 с, наступна сторінка 4,415 с. Час включає зовнішній MCP-транспорт.
Прискорення першого холодного читання не доведене; зменшено обсяг передачі
й повторні читання, робота історії не займає командний потік.

Код 0.3.16 вже використовував доступні Faza 1/2/3 як основний баланс, але
помилково залишав `power_source=fallback_inlet_stage` та `power_quality=estimated`
для всіх результатів. Через це примусово знижував статус точності й відсіював
перевірки потужності, навіть коли всі складові були свіжими.

Свіжий узгоджений баланс тепер має джерело `balance`, якість `measured`,
`measurement_basis=group_balance` та `independent=false`. Це розрахунок за
виміряними складовими, а не окремий прямий лічильник котла. Утримані тихі
значення лишаються оцінкою `fallback_group_balance`; номінальний резерв за
приладами — `fallback_inlet_stage`. Вони не стають точними навчальними мітками.
Невідоме живлення, застарілі джерела і суперечності не маскуються.

Загальна енергія включає origin + measured + estimated + recovered. Старі
лічильники, місячна база і попереднє відновлення зберігаються. Нові виміряні
прирости не зникають при переході між основним та резервним методом.

## Прогноз і його доказ — різні речі

Поточний прогноз на 24 години доступний незалежно від публікації графіка
відключень. Чинний планувальник уже розраховує довший горизонт для ранкового
запасу. Окремий компактний `sensor.heating_forecast_outlook` показує саме цю
наявну криву й сеанси, без нового пошуку. Кнопка повного горизонту з'являється
лише для того самого plan_id та горизонту понад 24 години. Невідома погода й
мережа залишаються умовними; фактичний grid та safety guards незмінні.
Суттєві зміни погоди та відключень проходять чинний механізм перепланування.

Завчасні прогнозні знімки незмінні. Перевірки температури не потребують
достовірної потужності чи повного outage schedule. Для кінця 24-годинної кривої
дозволена лише інтерполяція фактичної температури між реальними звітами, що
оточують точний контрольний час; максимальний розрив — менше з 90 хвилин та
1,5 типового інтервалу датчика. Такі результати мають
`actual_temperature_basis=interpolated_reports`, час порівняння й час звіту.
Прогноз не продовжується заднім числом. Якщо немає придатних звітів — перевірки
немає. Горизонти 36/48 год додаються тільки коли їх покриває початкова крива.

Температурні перевірки переживають reload. У таблиці видно кількість очікуваних
точок. Наявність прогнозу і запланованої перевірки не є доказом його точності:
довгий MAE з'явиться тільки після реальних завершених горизонтів.

## Швидкість історичного графіка

Передача зберігає protocol=2, range, request_id, result_id, offset і TTL.
Новий клієнт просить `compact=true`; `encoding=columns-v1` прибирає повторення
ключів і cycle_id. Маски зберігають різницю між відсутнім полем, null та нулем.
Жива перевірка виявила, що AppDaemon вилучає null-елементи масивів: тому
0.3.19 використовує позиційний placeholder 0 і sentinel `~` для явного null,
який обидва decoder повертають у пропуск. Значення температури 0 зберігається.
Старий клієнт отримує старий формат. Новий клієнт читає обидва формати.

Остаточний обробник у 0.3.18 — coroutine callback, який виконує блокувальну
роботу через `asyncio.to_thread`, не займаючи цикл подій AppDaemon.
Початковий `pin=false` у 0.3.17 виявився несумісним із конфігурацією,
де всі робочі потоки закріплені. Це відтворено на точному dispatcher
AppDaemon 4.5.13: coroutine dispatch проходить до вибору pinned/unpinned queue.
Налаштування потоків AppDaemon не змінюються.
Початкові запити використовують опублікований незмінний знімок історії, а
читання архіву виконується в executor. Окремий RLock захищає чергу запитів;
історичне читання не отримує права змінювати модель або обладнання.

Локальний benchmark однакових 3 003 справжніх архівних записів:

| Формат | Сторінок | Байти передачі | Медіана формування |
|---|---:|---:|---:|
| Попередній | 59 | 395 108 | 717,81 мс |
| Компактний | 28 | 204 872 | 96,14 мс |

Це ізольоване порівняння протоколу, не вимір часу завантаження через домашню
мережу. Оригінальні записи, температури, прогалини і прогнози збережені.

Перед комітом виконано `make check test`: 506 Python-тестів на Python 3.12
і 3.13, 46 JavaScript-тестів на Node 22; Python compile/import, JS syntax,
manifest та generated assets — успішно. Playwright Chromium/WebKit пройшли
наявний harness і перемикання 24/36 год на 320/390/1440 px. Дев'ять нових
Python-регресій покривають джерело потужності й суму двох класів енергії,
24-годинну кінцеву точку, 36 год без power/schedule, пропуски, повний compact
roundtrip, незмінні read snapshots, warm-cache/refresh і обмеження outlook 72 год.

Hotfix 0.3.18 додатково перевірено повним `make check test`: 510 тестів на
Python 3.12/3.13 та 46 Node 22 тестів, успішно. Чотири async-регресії перевіряють
вільний event loop під час блокувального worker, потік завершення, незмінний
read snapshot і передачу помилки. Окрема ізольована перевірка точного dispatcher
AppDaemon 4.5.13 відтворила стару помилку та підтвердила новий coroutine-шлях
за відсутності unpinned workers. Код теплового керування не змінюється.

Для 0.3.19 повний `make check test` пройшов на Python 3.12 (518 тестів,
183,075 с) і 3.13 (518 тестів, 133,691 с), Node 22 — 48 тестів.
Chromium/WebKit пройшли повний harness, включно з off/unknown мережею,
збереженим графіком та планом на 320/390/1440 px. Нові регресії спочатку
відтворили видалення прогнозу, відсутність перепланування, повторне
використання резервних ватів після втрати мережі й зсув compact-колонок.
Перевірка зі справжнім stable_plan сформувала 48 точок і майбутні сеанси
за невідомих ватів без команди heat. Повторний benchmark на тих самих
3003 записах у 0.3.19: 59 → 28 сторінок, 395108 → 202570 байтів,
найбільша нова сторінка 7598 байтів; відновлені записи ідентичні.
