- Return-water temperature remains a proxy/observer input, not floor-surface
  temperature. Selecting `fixed_6` describes the physical setting; it does not

- A missing advance forecast is shown explicitly. No model is rerun to create a
  past forecast. Missing points remain gaps, numerical zero remains zero.
- History protocol 2 uses request/result IDs, checked date bounds, immutable cached
  pages, at most 64 items and a 7,800-byte page payload. Results expire after ten
  minutes; at most four query results are cached. Reads run outside the controller
  callback. Duplicate/foreign pages cannot replace a client's result. REST recovers
  missed pushes without a delay per already available page.
- Old open panels get an explicit refresh explanation instead of a silent timeout.
  Reopen/reload Heating AI once after this UI transport update. No permission switch
  or manual AppDaemon stop is required.
- Current forecast projection v2 keeps 48 temperature/comfort points and session
  boundaries/total kWh, with session-average display kW. The full fine intervals,
  complete historical observations and search evidence stay private. The sensor's
  `actual_curve` is now a current marker; range history comes from the page protocol.
- Completed-cycle reports do not infer savings from incomplete low consumption.
  Positive excess with gaps is a lower bound; partial negative differences are not
  presented as proven savings. Legacy missing execution/thermal data stays absent.

## Archive capacity follow-up: 0.3.10

The owner requested an actual storage remedy. The physical disk had about 39 GB
free; the archive was at 257.9 MB of a 268.4 MB application limit. Lossless
compaction of closed daily journals already existed, so repeating it or deleting
protected snapshots would not solve the retention-capacity mismatch.

The default budget now estimates daily retained volume from existing file sizes
and timestamps, covers the configured retention plus two days, and adds 25%
headroom. It grows in 64 MiB steps only with known free space, to at most 1 GiB
and no more than 10% of spare disk above a reserve of max(2 GiB, 10% disk). The
reserve blocks new diagnostic writes before disk exhaustion, with a visible
error; control error handling remains intact. Explicit custom budgets remain
fixed. No archive format, snapshot identity, current settings, compression or
retention policy changes. Restart recalculates capacity without modifying old
files. An unknown disk reading never authorizes automatic expansion.

Five red-to-green tests cover capacity/preservation, explicit limits, restart,
low disk, unknown disk and the hard ceiling. All **437 Python tests** passed
on 3.12 (122.768 s) and 3.13 (121.174 s); **41 Node 22 tests** passed.
A three-run, 500-appends-per-run fixture measured median append 0.03669 ms before
and 0.03929 ms after; all resulting journals were the same 980,024 bytes. This
is a small added check cost, not a storage-performance improvement or a production
latency measurement.

Rollback of storage code preserves all files, but the old default 256 MiB budget
can again refuse new journal writes if the retained archive is larger. Therefore
prefer reverting only a defective control change while retaining capacity support;
do not delete data or restore an old state file as a code rollback.

## One-meter control reserve: 0.3.11

The owner requested continued control when one load meter fails, and confirmed
that the physical phase/group-to-appliance mapping is not known. A precise
replacement reading therefore cannot be inferred. For the existing balance,
`total − healthy load groups − signed inverter GRID` equals boiler power plus
the unknown group's consumption. The code retains the interval **0…remainder**;
it never assigns the missing group zero or calls the remainder a measured TEN.
The known water-heater load is already covered by a healthy group and is not
subtracted twice. LOAD/battery watts are not subtracted from GRID again.

`power_partial_reserve=enabled` is opt-in and requires the documented five-source
layout, exactly one unknown group, valid W/kW, fresh total/GRID with at most 30 s
skew, and the remaining groups within 90 s age/skew. Actual grid monitoring
remains authoritative. Only explicit fixed_3/6/9 profiles support the reserve;
unknown/AUTO profiles, two missing groups, missing core sources or contradictory
balances retain native fallback. Existing configurations default to disabled.

The separate control prior is the configured fixed rating capped by the residual
upper bound when the thermostat requests heat, otherwise zero. This is an
**assumption for approximate control**, not a measurement. Actual power remains
unknown in HA, history, energy accounting, physical heating markers and training.
The floor observer receives no unobserved heat or stale energy-counter delta;
missing inventory starts from the cooler of room/probe, not a hot pipe. A frozen
external counter does not turn reserve morning energy into confirmed zero kWh;
the coast safety check uses the hotter of the stored estimate and current return
probe. Room/probe validity, actual grid, permissions, allowed hours, outages,
thermostat acknowledgement and temperature protections continue to gate commands.

An estimated positive response is labelled `response_estimated`; it is never
`boiler_confirmed`. It cannot mask fresh measured zero, a disabled reserve or
stale reserve evidence. Accepted automatic morning requests accumulate separately
from confirmed heating, across adjacent observations at most 45 s apart. Their
planning credit prevents blindly repeating the minimum session; confirmed
minutes/kWh remain unchanged, and no request time is reconstructed after a gap.

The dashboard explains the degraded control mode and displays assumed calculation
power separately from unavailable actual consumption. Independent energy accuracy
and physical savings still require restored metering and completed cycles. The
reserve deliberately trades energy-observation precision for continued bounded
temperature control; it does not repair the offline Tuya device.

The final 0.3.11 candidate passes **451 Python tests** on 3.12 (59.924 s)
and 3.13 (60.018 s), **42 direct Node 22 tests**, and the full Chromium/WebKit

## Inlet accounting: 0.3.12

The owner requested replacement of the branch-meter method, rather than another
Faza fallback. `power_accounting_method=inlet` reads only the total and three
active-power channels of the inlet meter, configured non-overlapping consumers,
and the existing room/thermostat sources. It does not read the old power helper,
Faza fault flag or Faza readings. Actual grid permission still uses the existing
inlet-voltage / Deye guards; source timestamps are not refreshed by voltage.

Each physical consumer has one identity and ordered local/cloud aliases. Fresh
aliases must agree; only one is subtracted. Signed inverter GRID is deducted once;
LOAD, CT, battery power and devices already inside that branch are not added.
The production proposal contains the Deye GRID branch and the domestic water
heater's local/cloud aliases. Available observations distinguish the water heater
(~1.16 kW) from Deye LOAD (~0.16 kW); this is observational topology evidence,
not a verified wiring diagram. Other appliance meters are not blindly summed:
they may already belong to the inverter branch.

A stage must satisfy the aggregate residual, selected fixed profile (or AUTO),
thermostat request / >=0.5 °C demand, aligned fresh data and a feasible allocation
of at most one nominal 3 kW TEN per phase. Unknown load phases are enumerated,
not assigned from names. A 15-second stable candidate is required for heating.
Noise below 300 W may identify a pump/idle state. AUTO cross-checks a continuous
five-minute mean at stable return temperature against an independently validated
mode profile; absent calibration is labelled provisional and is not invented.

Nominal energy is **calculated**, never exact metering. The new persistent counter
starts once from the old total, leaves that HA entity unchanged, and integrates
only accepted nominal stages with a bounded 45-second hold and no restart gap
backfill. Monthly totals preserve the old month's starting value, prorate actual
integration across month/year boundaries, and start the next month at zero.
Cycle records retain measured balance energy and calculated nominal energy in
separate fields; both reduce the soft remaining plan without rewriting its initial
reference. Unknown gaps stay unknown. Nominal samples cannot train physical
coefficients or modulation, or certify independent forecast accuracy.

When classification is unavailable but core input data are fresh, the controller
may retain the existing conservative control prior and all safety vetoes. This
prior creates neither accounted energy nor stored floor heat. Missing consumer
power is not replaced by zero. A live pre-deployment example had an approximately
6.3–6.5 kW aggregate residual but phases near 1.6 / 1.6 / 3.2 kW; that cannot prove
two separate simultaneous 3 kW TENs. Averaged switching may still support a
nominal estimate when every residual phase stays below the single-TEN ceiling;
`phase_check=bounded_average` explicitly does not certify a physical TEN mask. Distinguishing an unmetered coincident heater from a TEN remains
physically unidentifiable without additional independent metering or wiring proof.

Rollback: select the previous accounting method, then install v0.3.11 through the
same coordinated HACS path if code rollback is necessary. Keep state.json and
all archives/counters; never restore the entire HA snapshot just to undo code.
New equipment keys live separately from ordinary overrides, so v0.3.11 ignores
those keys without invalidating the owner's existing settings.

The measured 38-second production full-planning callback remains a separate open
performance issue; inlet classification is not claimed to fix optimizer latency.
No physical energy-saving or nominal-meter accuracy claim is made before a new
completed heating cycle with independently interpretable inputs.
