# Heating AI V1 → нативний Marketplace: цільовий продукт і критерії готовності

**Статус: РОЗРОБКА / НЕ ВСТАНОВЛЮВАТИ.** Цей документ замінює попередню
ідею «просто доставити дев'ять Python-модулів із Marketplace».

## Однозначна ціль

**Один Marketplace-проєкт → установити інтеграцію → під'єднати існуючі
датчики й приватну історію → перевірити SHADOW → передати їй єдине
керування → наступні оновлення через Marketplace.**

Після фінальної міграції Heating AI працює **всередині HA Core через
нативну інтеграцію**; для його роботи не потрібні старий HACS,
AppDaemon, символьні посилання, окремий термінал, ручне копіювання
дев'яти модулів або другий керувальний процес.

Стара V1 залишається єдиним активним контролером до кваліфікованої
передачі керування. Sky Radar та інші застосунки AppDaemon не змінюються.

## Важливі обмеження поточного коду

Поточний ZIP-пакувальник лише забезпечує **доказ цілісності початкової V1
і переносимість її числового ядра**. `legacy_app/` — байтова копія для
контрактів і регресій, **не чинний runtime**. `native_engine/` — п'ять
чистих Python-модулів V1 з переписаними лише імпортами; жоден із них
не посилає команди. Нативна інтеграція-наповнювач `__init__.py`
сьогодні також **нічого не запускає**.

**Такий ZIP не є придатним для заміни контролера.** Не публікувати
реліз, не пропонувати установлення та не називати його готовою V1+.

## Джерела і що зберігаємо

- **Канонічна V1:** `dragonidf/ha-heating-ai`, PR #24, 9 модулів
  `apps/heating_ai/heating_*.py`, `VERSION`, `release.json`.
- **Донор V2:** `dragonidf/ha-heating-2`, PR #43;
  `packages/control/kernel.py`, HA-native quality/freshness,
  `critical_ledger.py`, `native_api.py`, тестова інфраструктура.
- **Без переписування математичного ядра V1:** `heating_model.py`,
  `heating_stability.py`, `heating_environment.py`,
  `heating_outages.py`, `heating_fallback.py`; однакові результати
  на однакових вхідних даних.
- **Поведінка V1 залишається:** день/ніч, комфортні межі, 30-хв ранковий
  прогрів, 3/6/9 кВт, інерція/обратка, камін, циркуляція, рекуператор,
  календар 3.1 та мережеві захисти, KWS, фіксована історія енергії,
  24-год план, прогноз-факт та навчання.
- **Критичне правило ручного режиму:** AUTO вибраний людиною не є
  доказом аварії. План залишається `advisory`, а не `intended`;
  без явного дозволу ніхто не вмикає нагрів після рестарту / reconnect.

## Архітектура готової V1+

1. `config_flow.py`: авторизоване одноразове підключення до чинних
   сутностей HA; імпорт приватних параметрів через явний сценарій
   резервування/валідації, без зберігання приватних даних у Git.
2. `native_engine/`: чиста теплотехніка V1 без залежності від HA чи
   AppDaemon; виходи відтворювані та перевірені проти V1 на реальних
   знеособлених/синтетичних знімках.
3. `source_adapter.py`: єдина типізована точка HA-читання;
   відокремлює свіжі підтверджені дані від last-known/unknown;
   ніколи не робить `unavailable=0`.
4. `runtime.py`: швидкі послідовні захисні перевірки та heartbeat;
   важкий пошук плану тільки окремо в bounded worker, single-flight,
   зі скасуванням застарілих результатів.
5. `command_gateway.py` + `critical_ledger.py`: CAS/epoch, один
   власник, durable journal, reconciliation after restart, no blind retry;
   захист режимів manual/fallback/one-shot, KWS і мережі.
6. `storage.py`: приватне стійке сховище поза каталогом Marketplace;
   атомарні snapshots, валідація схем, збереження лічильників без
   перепідрахунку, перевірений read-only migration/dry run.
7. `sensor.py` / `native_api.py`: status і діагностика без довгих
   історичних масивів у Recorder; повні план/факт через авторизований
   WebSocket API.
8. **UI V1+:** першим екраном є реальний графік (6 год факт + 24 год
   модель + планові нагріви + фактичні нагріви + цілі + відключення),
   далі налаштування і навчання/історія; мінімум технічного тексту,
   чіткі стани «виконується / advisory / fallback», робота на Android.
   Не переносити текстовий UI V2 як готовий.

## Порядок реалізації без зайвих циклів

**G0 — закриті базові тести:** PR #24 CI PASS; дев'ять модулів
фіксуються SHA-256; чиста модель V1 в новому Python namespace показує
однакові результати на ідентичних аргументах.

**G1 — нативна інтеграція у SHADOW:** встановлюється через Marketplace
і налаштовується config flow; запускає фактичний V1 planner і повну
панель на поточних HA джерелах; фізичні команди жорстко вимкнені;
немає другого контролера. Потрібна реальна перевірка на ізольованому
HA 2026.11 та потім read-only production.

**G2 — відповідність логіки:** порівняння 24-год плану, фактичних
інтервалів, моделі, КWS, прогнозу, каміна та циркуляції з робочою V1;
блокери виправляються у native adapter, не «поліпшенням» математичного
ядра без доказу.

**G3 — міграція приватної моделі та історії:** dry-run, резервна
копія, checksum, жодного скидання навчання, кВт·год чи прогноз-факт.
Облік енергії — лише дельти апаратного KWS, без подвійної інтеграції.

**G4 — ексклюзивний writer:** інвентар усіх авторів команд, включно
з watchdog HA, нічною циркуляцією, старим HeatingClimate;
доказ розриву старого owner/lease. Sky Radar залишається в AppDaemon.
Поки це не доведено, фізичний gateway V1+ завжди вимкнений.

**G5 — експлуатаційна перевірка:** `>=7` діб спостереження,
`>=3` повних циклів нагріву, виміряні затримки й пам'ять, повторний
старт Core, автоматичний fallback, ручна пауза, перевірений відкат.
Тільки потім окреме погодження cutover.

**G6 — реліз:** один immutable GitHub tag з root `hacs.json`,
`manifest.json` та справді встановлюваним ZIP. Повний контролер
працює після Marketplace install+setup; кожне наступне Marketplace
оновлення перевірене й потребує **одного перезапуску HA Core** за
чинною поведінкою 2026.11. Немає додаткового restart AppDaemon,
ручної синхронізації файлів чи залежності від HACS.

## Чого не робити

- Не перетворювати простий carrier ZIP на «готовий» контролер.
- Не видавати нативний SHADOW за повний runtime.
- Не запускати V2 як другого writer; не мігрувати V1 у V2.
- Не переносити все `heating_climate.py` з AppDaemon imports у HA Core.
- Не міняти модель, енергію, KWS, пороги без зафіксованого дефекту.
- Не зупиняти весь AppDaemon / Sky Radar.
- Не публікувати release до **усіх** gate-умов, включно з перевіркою
  Markdown/UI-панелі на реальному встановленні.
- Не починати повторно аудит; працювати з реальними файлами й
  обмеженими тематичними тестами.
