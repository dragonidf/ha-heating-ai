# Перевірка контролера 0.2.13

Базова версія: 0.2.12, main `28719a35d55b14805e3dc9fe220f3f4ea2cd1991`.
Один виконавець; без зміни архітектури, порогів каміна, політики планування,
HACS-координатора або налаштувань живого HA. Числові тести використовують
синтетичні вимірювання й підставний HA I/O, а не команди обладнанню.

## Підтверджені виправлення

- P1, `heating_model.py`: віднімання float відхиляло точну межу 20%, а абсолютний допуск 0,005 дозволяв значно більше для малих коефіцієнтів. Тепер спільні межі з допуском лише 8 ULP базового значення; фізичні межі залишаються строгими. До виправлення регресії меж/малих коефіцієнтів падали.
- P1, `heating_climate.py`: кілька прийнятих кандидатів могли накопичити понад 20% за добу. `learning_day` зберігає базу першої спроби за локальну дату Europe/Kiev. Перевіряються і поточна, і добова база; JSON round-trip не обнуляє ліміт.
- P1, `heating_climate.py`: прийнятий кандидат одразу замінював модель на неперевірену, що могло переводити керування в native fallback. За наявності перевіреної моделі кандидат тепер рахується на тих самих сеансах окремо, не керує котлом, і потребує щонайменше 12 підтверджених парних годинних похибок та поліпшення. Початкове навчання без перевіреної моделі зберігає попередню семантику.
- P1, `heating_recovery.py`: застаріле рішення могло виконатися після зміни дозволу/мережі/верхньої межі; native fallback без night helper не враховував денну верхню межу та відоме відключення. Нові тести відтворили ці команди до виправлення. Фінальні перевірки блокують їх, не розширюючи дозволені години або винятки.
- P1, `heating_climate.py`: пошкоджений стан мовчки замінювався порожнім або падав на неправильній структурі. Зараз файл збережений, проблема видима, команди вимкнено; старе відновлення енергії з втраченим state не виконується. Перезапис навчальної телеметрії атомарний.
- P2, навчання/UI: остання спроба містить дату, джерело, старі/запропоновані значення, delta, добову базу, кількості train/holdout та похибки лише якщо обчислені. Останній успіх окремий. Відхилений або pending кандидат не видається за поломку чинної моделі; нових persistent notifications немає.
- P2, Recorder: сумісне вилучення presence-based history flags через None перевірене транспортною регресією. Це не доказ єдиної причини всіх попередніх повідомлень `unverified`.

Нульовий коефіцієнт автоматично не змінюється. Явне редагування коефіцієнтів
користувачем проходить ті самі межі. Явний відкат відновлює попередню модель,
скасовує pending і не перебазовує добовий ліміт. Оновлення коду не скидає
чинні коефіцієнти або енергетичні лічильники. Після підтвердження нової моделі
стара довгогоризонтна статистика більше не вважається доказом для нової.

## Реальні спостереження та межі доказів

Під час підготовки живий `sensor.heating_ui` повідомляв 0.2.12,
`release_verified=true`, heartbeat був активний, модель v4 перевірена.
Прочитано опубліковані SHA усіх дев'яти модулів. Через незалежне читання
Recorder отримано 15 повних записів рішення, з однаковим state та різними
decision_id: атрибути фактично зберігалися. Приватні записи/конфігурація не
публікуються. Прочитана чинна погодна автоматизація: hourly/HA-start/manual
refresh → `weather.get_forecasts` → `heating_weather_forecast` → кеш. Вона вже
додає останню утриману температуру ще на годину; покриття кешу не є доказом
незалежного прогнозу постачальника на цю додаткову годину. Автоматизація не змінювалася.

Точний приватний snapshot попереднього інциденту через доступний транспорт
не відновлено; синтетичні регресії ранкового резерву його не замінюють.
Примусове навчання або фізичний нагрів не запускалися. Фізична точність
6/12/24-годинного прогнозу залишається непідтвердженою до накопичення
відповідних вимірювань; жоден тест не гарантує комфорт у реальному будинку.

## Обмежені вимірювання

Відтворення: `python tools/check_validation.py --output /tmp/heating-validation.json`.
CI зберігає лише знеособлений числовий звіт на 14 діб, без приватних входів.
Один локальний запуск на синтетичному сценарії з підставним HA I/O:

| Операція | Час |
| --- | ---: |
| Планування | 494,864 мс |
| Недостатній ранок, усі 3 проходи | 773,798 мс |
| Утримання перевіреного плану | 6,175 мс |
| Fast tick разом із fixture | 1,063 мс |
| Середній запис журналу | 10,012 мс |

12 записів повного перерахунку з повторюваною синтетичною траєкторією
зайняли 324065 байтів; лінійна оцінка 14 діб — 103,84 МіБ проти ліміту
256 МіБ і захищеного мінімуму 7 днів. Це не гарантія обсягу за частих змін
усіх входів. Планувальник залишається синхронним; реальна затримка AppDaemon,
диска та пристроїв не вимірювалася. Тести перевіряють кеш/обмежені проходи,
не нестабільний мілісекундний поріг. Чинний захист disk pressure зберігається.

## Оновлення та відкат

Це один реліз 0.2.13 через наявний HACS workflow після успішного CI main.
Потрібні чинні AppDaemon, helpers і локальний YAML за `installation.md`;
зовнішній ChatGPT для автономного керування не потрібний. Перед встановленням
зберегти резервну копію data_dir; штатний координатор сам зупиняє/відновлює
AppDaemon і дозволи. Після HACS перевірити версію, `release_verified`, heartbeat,
новий план, діагностику та відновлені armed/mode. Підготовлений реліз не означає
встановлення на HA. Для відкату коду використати попередній реліз HACS;
state.json/телеметрію/лічильники не замінювати порожніми. Відкат моделі — окрема
явна дія користувача, а не побічний ефект оновлення коду.

Локальний фінальний запуск: `make check test` — 277 Python-тестів успішно
(52,957 с), JS suite успішно; Python compile, синтаксис JS, актуальність
згенерованих assets/manifest перевірено. Chromium harness успішно перевірив
10 ширин 320–1920 px, включно з 360/390/430, теми, touch/rotation, стани
каміна/котла, warnings та статуси навчання. WebKit і Python 3.12/3.13
також входять до обов’язкового CI перед публікацією.
