# Автоматичне встановлення оновлень через HACS

Для поточного встановлення координатор HA підключено окремо. З 0.2.3 власнику достатньо натиснути **HACS → Heating AI — AppDaemon → Оновити**. Перемикати дозволи або вручну зупиняти/запускати AppDaemon не потрібно. Координатор автоматично перезапускає AppDaemon, тому його застосунки короткочасно призупиняються. HA Core не перезапускається.

## Що відбувається

1. `update.heating_ai_appdaemon_update.attributes.in_progress` запускає єдину транзакцію. HACS повідомляє початок до завантаження й заміни файлів. Координатор не перехоплює і не замінює дії самого HACS.
2. Початкові дозволи команд/циркуляції, стан запуску AppDaemon та попередня версія зберігаються в `input_text.heating_update_journal`. Локальні YAML, режим термостата, коефіцієнти, телеметрія й енергетичні лічильники не редагуються.
3. Обидва дозволи тимчасово вимикаються, AppDaemon зупиняється. Від 0.2.3 контролер додатково блокує ініціалізацію/команди під час `in_progress`. HACS не має синхронного pre-install hook: запуск координатора є реакцією HA на опублікований стан, а не гарантією блокування самого завантажувача.
4. Після закінчення HACS AppDaemon запускається, якщо працював до оновлення. Перевіряються версія `sensor.heating_ui` проти встановленої HACS, наявність контрольних сум дев’яти модулів, heartbeat після запуску й політика планування 4. Попередні дозволи відновлюються через тимчасову сцену лише після успішної перевірки. Дозвіл, який був вимкнений, не вмикається самовільно.
5. Результат з’являється в постійних сповіщеннях HA. Відкриту вебпанель оновити звичайним перезавантаженням сторінки.

Якщо HACS відновив попередню версію після невдалого завантаження, перевіряється та запускається вона. Якщо завантаження затягнулося, AppDaemon й дозволи залишаються призупиненими; періодична перевірка продовжує транзакцію. Якщо новий контролер не підтвердив роботу за три хвилини, дозволи залишаються вимкненими, журнал має `phase: failed`, створюється сповіщення. Автоматика не входить у нескінченний цикл перезапусків. Наступне встановлення HACS використовує початковий збережений стан дозволів.

Після перезапуску HA незавершена транзакція відновлюється з постійного журналу. Початковий стан не перезаписується вже призупиненими значеннями. Якщо AppDaemon був зупинений ще до оновлення, він залишається зупиненим. Увімкнення дозволу користувачем під час обслуговування не скидається старим знімком.

## Підключення на іншому встановленні

Це одноразове налаштування **HA**, не файли Python у каталозі HACS. Потрібні сучасні дії `hassio.app_stop` / `hassio.app_start` (HA 2026.2+) і доступна діагностична сутність AppDaemon `binary_sensor.appdaemon_running`. Якщо вона вимкнена інтеграцією, увімкнути її через реєстр сутностей і перезавантажити лише інтеграцію Supervisor.

Створити через API helpers відновлюваний `input_text.heating_update_journal` (максимум 255 символів) і встановити `idle`. Генератор [tools/hacs_workflow.py](../tools/hacs_workflow.py) повертає повний JSON конфігурації автоматики; його `build()` приймає перевірені slug/ідентифікатори конкретного встановлення. Створювати/оновлювати автоматику через офіційний API конфігурації HA або YAML-редактор її інтерфейсу, не через `.storage`. Спершу зберегти вимкненою, перевірити сутності й шаблони, потім увімкнути. Той самий генератор використовують офлайн-тести сценаріїв.

Тут `wait_template` потрібний, бо завантаження чи перевірка можуть уже завершитися до початку очікування. JSON-журнал потрібний для відновлення після перезапуску HA; тимчасові сцени не зберігаються між перезапусками. Шаблон перевірки JSON-фази не має відповідного нативного state-condition.

## Циркуляція від резерву

`input_boolean.heating_fan_backup_verified = on` підтверджує, що вентилятор фізично живиться від резерву. Власник поточного встановлення це підтвердив; параметр підготовлено для 0.2.3. Це окремо від живлення котла й не змінює визначення електромережі.

Без зовнішньої мережі потрібні одночасно підтверджений резерв, доступний інвертор зі свіжим heartbeat і доступний вентилятор. Helper має пріоритет над старим `fan_backup_verified` у YAML; його `unknown/unavailable` не означає підтвердження. За відсутності helper застосовується старий булевий параметр YAML. Для іншої назви helper передати `fan_backup` в локальному YAML.

Режими «Авто», «Зупинити», «Ручний запуск», дозвіл циркуляції й нічна межа швидкості зберігаються. Від 0.2.6 є [пороги, витримка вимкнення й три рівні циркуляції](fireplace-circulation.md). Вручну запущений вентилятор не привласнюється моделлю лише через зміну швидкості. Помилка команди вентилятора не переводить котел у резервний auto; однакова команда повторюється не частіше ніж раз на 30 секунд.

## Відключення координатора

Завершити транзакцію (`journal = idle`) й вимкнути автоматику «Heating AI — автоматичне оновлення HACS». Це повертає ручний порядок оновлень з [інструкції встановлення](installation.md). Не очищати незавершений журнал до збереження початкових дозволів. Helper резервного живлення не видаляти: для зміни схеми живлення зняти підтвердження й скоригувати його початкове значення в налаштуваннях helper.
